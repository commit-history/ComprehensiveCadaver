## Core Components

### 1. Data Models

**Deck Model** (decks.json)
- Hierarchical organization: Deck → Subdeck → Cards
- Tracks which cards belong to which subdeck
- Used by build pipeline to structure output

**Card Model** (individual .json files)
- Complete definition of one card
- Contains: metadata, image, front/back text (multilingual), annotations
- Used by web UI for editing
- Input to build pipeline

See: **DATA_MODEL.md**

### 2. Web UI

**Technology:** React (or Vue/Svelte)

**Main Screens:**
- **Deck Browser**: Hierarchical deck/subdeck list with card counts
- **Card List**: Filterable list of cards in selected subdeck
- **Card Editor**: Front/back tabs with text editors, image canvas, annotation editor

**Key Features:**
- Multi-language text editing with translation tracking
- Visual annotation editor (place labels, arrows, overlays)
- Real-time preview of annotations on image
- Search & filter (by deck, tags, translation status)
- Auto-save with conflict detection

See: **UI_REQUIREMENTS.md**

### 3. Build Pipeline

**Technology:** Python script

**Steps:**
1. Load all card JSON files
2. Validate against deck hierarchy
3. Copy images to media/ folder
4. Convert each card → Anki note
5. Organize notes into deck structure
6. Generate deck.json (CrowdAnki format)

**Input:** `cards/`, `images/`, `decks.json`
**Output:** `deck.json`, `media/`

See: **BUILD_PIPELINE.md**

### 4. Anki Integration

**No changes needed** to existing Anki deck templates or configuration.

**Import process:**
1. User runs build script (generates deck.json)
2. In Anki: File → CrowdAnki: Import from disk
3. CrowdAnki merges new/updated cards with existing deck
4. Review history & scheduling preserved

**Update process:**
- Edit cards in web UI
- Run build script again
- Re-import deck.json
- CrowdAnki matches cards by GUID and updates

## File Organization

### cards/ Directory

**Purpose:** Store individual card definitions

**Structure:**
```
cards/
  {deck_id}/
    {subdeck_id}/
      {cardId_1}.json
      {cardId_2}.json
      ...
```

**Example:**
```
cards/
  abdomen/
    vessels/
      AbdomenCeliac_Anterior.json
      AbdomenCeliac_Posterior.json
    nerves/
      AbdomenVagus_Anterior.json
  upper-limb/
    osteology/
      UpperLimbHumerus_Anterior.json
      UpperLimbRadius_Anterior.json
    nerves/
      UpperLimbBrachialPlexus_Anterior.json
```

**Rationale:**
- Mirrors deck hierarchy (easy to navigate)
- One card per file (git diff-friendly)
- Directory structure matches UI navigation

### images/ Directory

**Purpose:** Store source images for cards

**Structure:**
```
images/
  {deck_id}/
    {subdeck_id}/
      {imageName}.jpg
```

**Example:**
```
images/
  abdomen/
    vessels/
      celiac_anterior.jpg
      celiac_posterior.jpg
      sma_anterior.jpg
    nerves/
      vagus_anterior.jpg
```

**Build process:**
- Images copied to `media/` folder (flat structure)
- Filenames transformed: `abdomen/vessels/celiac_anterior.jpg` → `abdomen_vessels_celiac_anterior.jpg`
- References in deck.json point to flattened names

### decks.json

**Purpose:** Define deck hierarchy (single source of truth)

**Structure:**
```json
{
  "decks": [
    {
      "id": "abdomen",
      "name": "Abdomen",
      "order": 1,
      "subdecks": [
        {
          "id": "abdomen-vessels",
          "name": "Vessels",
          "order": 1,
          "cardIds": ["AbdomenCeliac_Anterior", "AbdomenSMA_Anterior"]
        }
      ]
    }
  ]
}
```

**Constraints:**
- All referenced cardIds must exist in `cards/`
- All deck/subdeck IDs must be unique
- Must be valid JSON

## Data Validation

### Build-time Validation

Performed by build script before generating deck.json:

1. **Card file integrity**
   - All required fields present
   - Image files exist
   - Text has at least one language
   - Annotation bounds within image dimensions

2. **Deck hierarchy consistency**
   - All cardIds referenced in subdecks exist
   - No orphaned cards (cards not in any subdeck)
   - No duplicate cardIds
   - Deck/subdeck IDs match references

3. **Translation completeness**
   - Tracked per card (complete/partial/missing)
   - Reported in build output

### Runtime Validation (Web UI)

Performed as user edits:

1. **Field validation**
   - Card ID must be unique
   - Title required
   - At least one language per text field
   - View axis must be valid enum

2. **Constraint validation**
   - Annotation bounds within image dimensions
   - Polygon overlays have ≥3 nodes
   - Bounding box coordinates valid (topLeft ≤ bottomRight)

3. **Feedback**
   - Red border on invalid fields
   - Toast notifications on save errors
   - Prevent save if invalid

## Key Design Decisions

### 1. Card Granularity
**Decision:** One card per file

**Rationale:**
- Git-friendly (better diffs, conflict management)
- Parallel editing (multiple users on different cards)
- Easier to version/rollback individual cards

### 2. Image Duplication
**Decision:** Separate image folders for source, flatten during build

**Rationale:**
- Keep directory structure organized
- No image duplication in source (images/ → media/ copy)
- Flat media/ structure matches Anki expectations

### 3. Deck Hierarchy
**Decision:** Single decks.json file (vs. distributed per-deck)

**Rationale:**
- Single source of truth
- Ensures consistency
- Easy to reorder or restructure

### 4. Text Translations
**Decision:** Embedded in card JSON (vs. separate translation files)

**Rationale:**
- Keeps card definition self-contained
- No external dependencies when editing
- Translation status easily computed (check field presence)

### 5. Annotations in Source
**Decision:** Store annotations in card JSON (not rendered in Anki)

**Rationale:** (Current)
- Flexible (future rendering options)
- Easier to edit/debug

**Future Option:** Render annotations server-side for import into Anki

## Development Workflow

### Adding a New Card

1. **Create card directory structure:**
   ```bash
   mkdir -p cards/abdomen/nerves
   mkdir -p images/abdomen/nerves
   ```

2. **Extract/prepare image:**
   - Export from PPT as JPEG
   - Save to `images/abdomen/nerves/new_nerve.jpg`

3. **Create card JSON skeleton:**
   ```bash
   # Web UI → New Card
   # Or manually create JSON file
   ```

4. **Edit in web UI:**
   - Add front/back questions
   - Add translations
   - Add annotations
   - Save (creates JSON file)

5. **Run build pipeline:**
   ```bash
   python build_deck.py
   ```

6. **Import to Anki:**
   - In Anki: File → CrowdAnki: Import from disk
   - Select project root

### Updating Translations

1. Open card in web UI
2. Select language from dropdown
3. Type translation
4. Save (updates JSON file)
5. Run build pipeline
6. Re-import to Anki (updates only changed notes)

### Reordering Cards

1. Edit `decks.json` (move card ID to different position)
2. Run build pipeline
3. Re-import to Anki (preserves review history)

## Performance Considerations

### Web UI

- **Virtualized card list:** Only render visible cards (handle 1000+ cards)
- **Lazy image loading:** Load thumbnails first, full image on demand
- **Debounced search:** 300ms debounce to avoid excessive re-renders
- **IndexedDB caching:** Cache card data locally to reduce HTTP requests

### Build Pipeline

- **Streaming JSON parsing:** Handle large card directories
- **Parallel image copying:** Use concurrent file operations
- **Lazy validation:** Only validate changed cards on incremental builds

### Deck Size

Current architecture supports:
- **Up to 10k cards** (reasonable for comprehensive anatomy deck)
- **Unlimited translations** (no performance impact)
- **Unlimited annotations per card** (stored as array, no performance impact)

## Summary

The system provides a **complete workflow** for creating multilingual, annotated anatomical cards:

1. **Web UI** for non-technical users to define and edit cards
2. **Structured data model** for cards and deck hierarchy
3. **Build pipeline** to convert to Anki-compatible format
4. **CrowdAnki integration** for seamless import

All pieces work together to enable:
- ✅ Easy card creation/editing
